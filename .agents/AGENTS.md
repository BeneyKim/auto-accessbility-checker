# ThinQ Web Accessibility Checker 프로젝트 행동 규칙

> [!IMPORTANT]
> **에이전트 실수 및 Lessons Learned 준수 고지**
> 모든 개발 및 분석 단계에 착수하기 전, 에이전트는 반드시 [.agents/AGENT_MISTAKES.md](file:///c:/Users/bhkim/projects-codex/ibm-assessbility-checker/.agents/AGENT_MISTAKES.md) 파일을 사전에 읽고, 그곳에 기록된 23대 실수 사례(로그 미확인 추측 수정, 단순 URL 목록 판별, 탭 상태 캐시 유실 등)를 철저히 우회하여 설계해야 합니다.

1. 소스 코드 수정 전에 반드시 구체적인 원인 분석과 개선 방안을 문서로 작성하여 보고하고, 사용자의 리뷰 및 최종 승인을 받아야 합니다.
2. 사용자의 명시적인 승인 없이 임의로 코드를 수정하거나, Terminal 명령어를 실행하거나, Git Commit/Push를 수행해서는 안 됩니다.
3. 모든 작업 시 side effect(기존 기능 퇴화)가 발생하지 않도록 철저히 검증하고 관련 Unit Test를 동반하여 추가해야 합니다.
4. 질문에 대해 정확하지 않은 대답은 하지 않고 데이터를 확인하고 대답한다.
5. 기능 설계 및 수정시 브라우저의 제약이 없는지 확인한다.
6. 모든 원인 분석 및 코드 수정 시 짐작이나 추정이 아닌, 제공된 실제 로그 파일의 원본 데이터(접근성 이름, 속성명 등)를 대조·확인하여 정확한 원인을 진단하며, 해당 실제 데이터 패턴을 모방한 단위 테스트(Unit Test)를 필수로 추가하여 검증한다.
7. 상태 지시자/스위치(switch-toggle, static text) 제외 규칙 등 크롤링 후보 필터링을 구현할 때, 자식/후손 노드의 상태 텍스트 패턴이 전파되어 부모의 정상적인 대화형 요소(`button`, `a`, `role="button/link/tab"`)까지 스킵을 유발하지 않도록, 강한 인터랙티브 요소는 직접적인 스위치/체크박스/라디오 컨트롤이 아닌 한 제외 처리에서 기본 면제(bypass)되도록 방어 코드를 설계하고, 이에 대한 단위 테스트를 필수로 추가하여 검증해야 합니다.
8. **로그 기반 3단계 교차 검증 원칙**: 모든 원인 분석, 수정 후 동작 검증, 단위 테스트 DOM 설계는 오직 '원본 로그 데이터 패턴(TransitionLog, 시그니처 텍스트 등)'을 대조하여 검증해야 합니다. 짐작이나 추측에 의한 수정은 절대 금지합니다.
9. **단위 테스트 모킹 및 사이드 이펙트(Side Effect) 확인**: 단위 테스트 작성 시 실제 로그에 노출된 고유한 DOM 속성(aria-selected, data-name, class 등)과 위배 패턴을 완벽히 모킹(Mocking)해야 하며, `npm run verify`를 실행하여 기존 기능에 퇴화(Regression)나 영향이 없는지 재차 확인해야 합니다.
10. **가전 모듈별 이탈 방어 규칙**: 스마트진단이나 마이크 하드웨어 제어 등 앱 외부로의 이탈을 초래하는 위협 노드는 조상 8레벨까지 및 Shadow DOM host까지 검출하도록 충분한 깊이의 필터를 적용해 원천 스킵해야 합니다.
11. **SPA 탭 구조 내비게이션 격리**: 단일 DOM 상에서 활성/비활성에 따라 영역이 토글되는 SPA 탭 구조(제품 vs 유용한 기능 등)를 크롤링할 때, 비활성 상태인 탭 버튼(`aria-selected="false"`)에 속한 콘텐츠 패널 하위의 엘리먼트들은 후보 수집 단계에서 엄격히 분리·제외하여 교차 오작동을 차단해야 합니다.
12. **Waiver 및 중복 진입 경로 차후 최적화**: 가전 모듈별(GWM, GPM 등)로 명확한 중복 진입 경로(예: 제품탭 최근 사용 코스 vs 유용한 기능탭 사용 이력)가 존재하는 기능에 대해 클릭 스킵 목록을 설계하고, 예외 룰셋 처리를 통해 크롤러의 효율성을 극대화하도록 개선안을 유지합니다.
