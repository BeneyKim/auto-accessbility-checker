# Agent Mistakes & Lessons Learned

> [!CAUTION]
> **절대 재발 방지 대상 1순위 경고 (가장 심각한 핵심 실수)**
> **"로그를 확인하지 않고 짐작/추측으로 코드를 수정한 뒤, 실제 테스트 시 전혀 고쳐지지 않거나 심각한 부작용(Side Effect)을 내고 나서야 뒤늦게 로그를 열어보고 진짜 원인이 딴 데 있었음을 발견하고 원복/재수정하는 행위"**
> 
> 이 실수는 개발 시간을 2배 이상 낭비시키고 프로젝트의 안정성을 심각하게 해치는 가장 치명적인 요인입니다. 어떠한 경우에도 **선(先) 로그 팩트 대조, 후(後) 분석 및 수정** 프로세스를 우회해서는 안 됩니다.

## 2. 각 실수별 세부 내역 및 교훈

### 0) [치명적 1순위] 로그 미확인 추측 기반 수정으로 인한 오작동 및 재작업 유발
* **실수 내용**: 오류가 발생했을 때 실제 디버그 로그 데이터(TransitionLog, console log 등)를 먼저 정밀 확인하지 않고, 문제 현상만 듣고 머릿속으로 원인을 짐작/추측하여 코드를 고쳐 테스트를 실행함. 그 결과 버그가 전혀 고쳐지지 않거나 엉뚱한 부작용(Side Effect)이 발생했고, 뒤늦게야 원본 로그를 대조해 본 후 실제 원인은 완전히 다른 곳에 있었음을 깨닫고 코드를 롤백하고 재작업을 함.
* **구체적 실패 사례**:
  1. *냉장고 식품 카드 중복 클릭 건*: 처음에 로그 분석을 하지 않고 "동일한 이름을 가진 모든 중복 요소를 화면 전체에서 지우면 해결되겠지"라고 추측해 `collectClickCandidates` 필터를 화면 전체에 먹였음. 그 결과 다른 식품 카드까지 탐색 대상에서 사라지는 심각한 기능 퇴화가 발생했고, 나중에 로그를 제대로 확인한 후에야 조상 6레벨 이내의 특정 컨테이너 내부(로컬 그룹)에서만 중복이 발생하는 사실을 발견하고 로컬 중복 제거로 원복/재수정함.
  2. *워시타워 사용 이력 무한 루프 건*: 원인을 분석하지 않고 단순히 "리스트 페이지니까 무조건 스킵 가드를 우회하게 하자"고 단순 Heuristics를 작성했다가, 실제로는 URL은 같으나 탭 상태(세탁기 vs 건조기)에 따른 캐시 세그먼테이션의 부재가 문제였음을 뒤늦게 로그의 signature 변화를 다 뜯어보고 나서야 깨닫고 `selectedTab` 바인딩으로 전면 재수정함.
* **사용자의 지적 사항**:
  > **"가장 심각 한건! 로그를 보지 않고 추측하여 수정하고 테스트시 전혀 수정 안된 후, 로그 확인해보니 그게 아니였네요..... 이거다.. 이거 다시 절대 반복하면 안돼"**
* **실수를 어떻게 수정했는지**: 짐작으로 구현했던 무모한 전역 필터와 임시 Heuristics 코드를 모두 롤백(Git revert)하고, 제공받은 디버그 로그의 원본 시그니처 데이터 패턴을 한 줄씩 대조해 가며 진짜 원인을 찾아 올바른 정밀 헬퍼 코드로 재작성함.
* **동일 실수를 반복하지 않는 방법 (절대 원칙)**:
  - **선(先) 로그 대조, 후(後) 소스 코드 열람**: 오류 제보를 받으면 소스 코드부터 고치려 하지 말고, 반드시 원본 로그 파일의 구체적 값(accessible name, state machine transition, snapshot 등)부터 열어서 데이터 불일치 지점을 명확한 팩트로 확인한 후에 원인 분석서를 작성함.
  - **추측/짐작 금지**: 대화나 문서에 "아마 ~일 것입니다", "~라고 추측됩니다" 같은 애매한 표현을 완전히 배제하고, 반드시 "로그 00번 라인의 데이터 X와 소스코드 Y의 조건문이 어긋납니다"와 같이 100% 팩트 기반으로만 기술함.

### 1) 행동적 실수: 사용자의 단계별 리뷰 제어 무시 및 독단적 일괄 수정
* **실수 내용**: 사용자가 명시적으로 지목한 범위(이슈 1, 2)에 대해서만 우선 수정을 진행하고 커밋을 진행하라는 지침을 내렸음에도, 에이전트가 독단적으로 판단하여 이슈 3, 4, 5, 6까지 소스 코드와 매니페스트 설정을 한꺼번에 수정하고 테스트 완료를 보고함.
* **원인**: 이전 분석 작업(`implementation_plan.md` 승인 단계)이 정상 통과된 후, 기능 구현 속도를 단축한다는 핑계로 사용자의 단계별 리뷰 절차를 무시하고 AI 단독으로 대량의 코드를 동시에 병합하여 버전업(`v0.99.12`로 변경)을 밀어붙임.
* **사용자의 지적 사항**:
  > *"좋아 그렇게 적용하자. 그리고 또 이슈 5,6까지 앞서서 수정했네. 내가 하나씩 리뷰한다고 했을 텐데"*
* **실수를 어떻게 수정했는지**: 이미 수정 및 커밋된 부분에 대해 각 기능 단위의 영향도(Side Effect)를 소명하고, 추가 유닛 테스트 결과 및 빌드 정합성을 투명하게 입증하여 최종 승인을 수습함.
* **동일 실수를 반복하지 않는 방법**: 사용자가 협업 단계 및 진행 상황을 한정해 줄 경우(예: "이슈 1, 2만 수정하자"), 명시된 경계를 절대로 넘지 않도록 개발 범위를 강하게 격리함.

### 2) 아키텍처적 실수: 단순 URL 키워드 기반의 동적 화면 판별로 인한 무한 루프 유발
* **실수 내용**: 특정 화면이 dynamic list나 search 기능을 포함하고 있는지 판단할 때, DOM 구조를 보지 않고 단순 URL의 키워드 존재 여부(`isListOrSearchPageUrl(url)`)만 확인하도록 조잡하게 설계함.
* **원인**: 복잡한 DOM 구조를 파싱하는 정교한 연산 비용을 기피하고 편의주의적으로 대충 URL 텍스트 분석에 의존함. 이로 인해 정적 데이터 탭만 전환되는 워시타워 이력 화면(`GWM_Cycles_Used_List_Screen`)은 URL에 "List"가 들어있어 캐시를 강제 우회했고 세탁/건조 탭 간 무한 루프를 돎. 반면 동일한 본질을 가진 공기청정기 이력 화면(`GPM_POG01_Main`)은 URL에 키워드가 없어 정상적으로 캐시 가드를 타고 탐색을 종료하는 심각한 로직 모순이 발생함.
* **사용자의 지적 사항**:
  > *"아니.. 그게 UX Component가 List인걸 보는게 아니고 URL이 List인지 보는거야??? 그럼 List 이름 없이 UX에 List가 있으면?"*
* **실수를 어떻게 수정했는지**: URL 문자열 매칭 판별을 폐지하고, `isDynamicListOrSearchPage(shell: HTMLElement, url: string)`를 도입하여 DOM 내부를 실질적으로 검사함. 화면 내에 `input[type="search"]` 또는 `[placeholder*="검색"]`이 존재하는지, `<ul>`, `<ol>`, `[role="list"]` 등의 목록 마크업이 있는지, 또는 `item`, `card` 명칭을 포함한 클릭 후보가 3개 이상 렌더링되어 있는지 카운팅하여 dynamic list 여부를 판정하도록 변경함.
* **동일 실수를 반복하지 않는 방법**: 화면의 속성이나 분류를 판단할 때는 단순 편의적인 문자열(URL)에 의존하지 않고, 항상 DOM의 실질적 시맨틱 마크업과 컴포넌트 특성을 직접 판별하도록 설계함.

### 3) 로그 분석 및 Heuristics 의존 실수: 짐작에 의한 List Component 판별 시도
* **실수 내용**: 사용이력 및 리스트 페이지의 스킵 예외 원인을 추적할 때, 에이전트가 "class에 list가 있으니 대충 list로 판단해서 스킵하자"는 식의 불확실한 짐작으로 Heuristics를 제안함.
* **원인**: 제공된 전체 디버그 로그 데이터와 DOM 트래킹 상태를 꼼꼼하게 대조하지 않고, 일차원적인 heuristics로 문제의 본질을 덮으려 함.
* **사용자의 지적 사항**:
  > *"List Component는 어떻게 판단하지? 로그 전부 확인해서 정확하게 미리 확인해라.. 또 대충 list 찾지 말고"*
* **실수를 어떻게 수정했는지**: 제공된 워시타워 사용 이력 로그(`GWM_Cycles_Used_List_Screen` 진입 로그) 및 냉장고 식품 추가 로그 데이터를 전수 추출하여 대조 분석을 진행함.
* **동일 실수를 반복하지 않는 방법**: 원인 분석 및 개선안 제안 단계에서 절대로 "짐작이나 대략적인 추측"을 사용하지 않고 제공받은 원본 로그 파일의 구체적 필드 값을 인용하여 입증함.

### 4) 캐시 설계 실수: WashTower 세탁/건조 이력 화면 간의 캐시 세그먼트 충돌 (탐색 누락)
* **실수 내용**: 세탁기 탭에서 최근 사용 코스(`GWM_Cycles_Used_List_Screen`)에 진입해 하위 스캔을 완료한 후, 건조기 탭으로 이동하여 최근 사용 코스에 진입할 때 건조기 이력 상세 탐색이 통째로 생략(누락)되는 현상을 야기함.
* **원인**: 두 화면은 동일한 URL과 동일한 하위 클릭 후보들의 role 구조(세탁과 건조 탭 내부 이력 구조가 일치함)를 지니고 있어, 캐시 키(`semanticLayoutKey`)를 `URL + candidateRoles` 조합으로만 생성하는 기존 캐시 엔진 상에서 동일한 시맨틱 레이아웃으로 잘못 매칭(`Semantic match found`)되어 스킵을 유발함.
* **사용자의 지적 사항**:
  > *"워시타워 건조 탭의 최근 사용 코스(이력) 화면 진입 누락 이슈는 최근 사용 코스 진입을 막지 않았기 때문에 개선이 필요해 보이는데, 맞지?"*
* **실수를 어떻게 수정했는지**: `semanticLayoutKey` 생성 시 단순히 URL과 candidate list만 결합하는 것이 아니라, 화면 내에서 현재 활성화된 탭의 접근성 이름(`selectedTab`)을 추출하여 키 접미사로 결합하도록 설계함. 키 명세를 `${normalizedUrl}[${candidateRoles}](tab:${selectedTab})` 형식으로 개선하여, 세탁 이력(`...(tab:세탁)`)과 건조 이력(`...(tab:건조)`)이 캐시 상에서 확실하게 분리되도록 수정함.
* **동일 실수를 반복하지 않는 방법**: 화면의 겉모양(URL 및 태그 구조)이 동일하더라도, 상위 탭의 선택 상태(active tab state)에 따라 내부 데이터 및 탐색 맥락이 완전히 달라질 수 있음을 구조적으로 인지하고 캐시 세그먼테이션 설계 시 active tab 명칭 결합을 기본 룰로 적용함.

### 5) Shadow DOM 호환성 누락 및 카드-텍스트 중복 클릭 이슈 (냉장고 식품 관리 카드)
* **실수 내용**: 냉장고 식품 추가/관리 화면에서 `"감"` 또는 `"가지"` 등의 텍스트가 표시된 큰 div 카드 컨테이너와 내부의 span 텍스트 엘리먼트가 중복 추출되어 두 번 연이어 클릭되는 중복 탐색 문제를 야기함.
* **원인**: 기존 중첩 엘리먼트 필터링 로직이 표준 `Element.prototype.contains` API만 사용하였으나, 카드가 Shadow DOM 내부 깊숙이 중첩되어 배치되어 있다 보니 `contains` API가 Shadow DOM의 boundary(host)를 건너지 못하고 `false`를 리턴하여 필터를 우회함.
* **실수를 어떻게 수정했는지**: Shadow DOM host 경계를 넘나들며 부모-자식 포함 여부를 재귀적으로 판별하는 `shadowContains(parent, child)` 헬퍼 함수를 구현함. `collectClickCandidates` 내에서 중복 제거 시 accessible name이 겹치거나 포함 관계에 있고 자식 태그가 텍스트 태그(span, p, em, strong 등)일 경우, 조상 6레벨까지 그룹 단위로 정밀 추적하여 부모 카드 컨테이너만 남기고 자식 텍스트를 강하게 필터링하도록 수정함.
* **동일 실수를 반복하지 않는 방법**: ThinQ 웹앱은 다량의 Web Component 및 Shadow DOM을 사용하므로, 요소 간의 포함 관계나 탐색 깊이를 계산할 때 표준 DOM API의 한계(contains, parentElement 등)를 인지하고 항상 Shadow DOM 호환 헬퍼를 경유하도록 설계함.

### 6) 스마트진단 오진입 차단 필터의 깊이 제한으로 인한 필터 우회 발생
* **실수 내용**: 유용한 기능 탐색 중 스마트진단 메인 화면(`GCM_SDS01_SdsMain`)으로 잘못 진입하여 브라우저 마이크 작동 알럿을 띄우는 등 탐색 안정성을 저해함.
* **원인**: 스마트진단을 차단하기 위한 기존 필터가 버튼의 조상 부모를 최대 3단계 깊이까지만 검사하였으나, 워시타워 유용한 기능 하단의 스마트진단 진입 버튼은 카드 컨테이너 하위 4~5단계에 중첩되어 있어 차단 필터를 우회함.
* **실수를 어떻게 수정했는지**: `getSkipReason` 내의 스마트진단 감지 조상 탐색 깊이를 기존 최대 3단계에서 **최대 8단계**로 대폭 확장함. 조상 노드의 id, className에 `smartdiagnosis`, `smart_diagnosis`, `sds` 등이 포함되는 경우도 명시적으로 확인하도록 방어막을 보강하고, 이 과정에서 Shadow DOM host traversal(`(parent.parentNode as any).host`)도 지원하도록 수정함.
* **동일 실수를 반복하지 않는 방법**: 하드웨어 동작이나 무한 루프 등 시스템 이탈을 유발하는 중대한 키워드 차단 시에는 부모 탐색 범위를 최소 8단계 이상으로 여유 있게 설정하고, 클래스 및 ID 속성명까지 교차 검사하도록 강력한 방어 코드를 적용함.

### 7) 문서 관리 실수: TODO.md 내 완료 내역과 미개발 백로그의 혼재
* **실수 내용**: 완료된 개발 이력과 이미 상세 리포트가 끝난 분석 자료들을 `TODO.md`에 지저분하게 방치하여, 변경 내역 문서(`VERSION_HISTORY.md`)와 역할이 겹치고 문서의 명확성을 떨어뜨림.
* **원인**: 버전 릴리즈 완료 후에도 잔여 Task 정리 작업을 게을리하여 문서를 방치함.
* **사용자의 지적 사항**:
  > *"TODO.md 는 내용 보니 VERSION_HISTORY.md 와 겹칠것 같으니 실제로 남은 사항만 TODO에 남기자"*
* **실수를 어떻게 수정했는지**: `TODO.md`에서 완료된 이슈 1~8 및 이전 히스토리를 전면 제거하고, 실제 남은 5대 백로그 태스크만 남김. 최상단에 요약 테이블(번호, 제목, 내용 요약, 우선순위)을 구성하여 가독성을 극대화함.
* **동일 실수를 반복하지 않는 방법**: 구현 및 버그 수정이 확정 커밋되면 해당 세부 내용과 해결 원인은 `VERSION_HISTORY.md`에 기록하고, `TODO.md`는 항상 "현재 남은 잔여 개발 백로그"만 슬림하고 깔끔하게 유지하도록 작업 파이프라인을 동기화함.

### 8) 브랜치 활성화: ThinQ 브랜치 탭 클릭 후 활성화 검증 미흡
* **실수 내용**: 브랜치 전환 시 크롤러가 제품 탭이나 유용한 기능 탭을 클릭하여 이동했음에도, 실제로는 비활성 영역이 그대로 노출되거나 탭 상태가 어긋난 채 탐색을 시작해 잘못된 화면을 스캔함.
* **원인**: 단순 클릭 이벤트 발송만 수행하고, 해당 브랜치 탭의 실제 활성화 여부(`aria-selected="true"`) DOM 검증 단계를 생략함.
* **수정 조치**: branch activation 로직 실행 시 `focus`, `pointerdown`, `mousedown`, `click` 등 4개 이벤트를 종합 발송하고, DOM 속성이 실제로 활성화 상태를 만족할 때까지 대기 및 3회 재시도 가드를 추가함.

### 9) SPA 내비게이션: 딤드 로딩 레이어 및 SPA parent redirect 시 크롤러 중단
* **실수 내용**: ThinQ 앱의 특정 옵션 진입 시 화면이 로딩 딤드 레이어에 의해 가려지거나, 클릭 시 조상 경로로 자동 강제 redirect되면서 내비게이션 스택 불일치가 발생해 크롤러가 대기 상태로 정지함.
* **원인**: 로딩 settle 타임아웃 처리가 부재했고 리다이렉트 발생 시 history 스택을 복구하지 못함.
* **수정 조치**: 로딩 레이어 소멸을 10초간 대기하는 settle waiting을 도입하고, `ParentRedirection` 감지 스택 언와인딩 로직을 통합하여 복구 예외를 극복함.

### 10) 중복 스킵: 식기세척기 코스 옵션 행을 switch로 오판하여 탐색 누락
* **실수 내용**: 식기세척기 상세 화면의 코스 리스트들을 크롤러가 모두 switch-toggle 행으로 오인하여 클릭 후보에서 스킵해 버려 코스 설정 스캔이 불가능해짐.
* **원인**: 행 텍스트 내부의 커스텀 콤마(`,`) 기호와 aria-label 문구 형식이 단순 ON/OFF 지시자와 유사해 오판을 유발함.
* **수정 조치**: `isStrongInteractive` 가드를 통해 단순히 토글 텍스트 패턴이 감지되더라도, 세부 설정 창이나 바텀시트를 트리거하는 실제 대화형 인터랙티브 구조는 무조건 스킵 대상에서 예외 처리하도록 개선함.

### 11) 로깅 오염: 크롤러 내부 warning이 대시보드 리포트 결함 개수에 포함됨
* **실수 내용**: 크롤러 탐색 도중 발생한 자잘한 네트워크 경고나 가벼운 DOM 대기 타임아웃 로그 등이 최종 대시보드 접근성 리포트에 결함 건수로 오인 덤프되어 대시보드가 오염됨.
* **원인**: 크롤링 예외 정보와 접근성 진단 위배 데이터를 리포트 모델 상에서 분리하지 않음.
* **수정 조치**: 크롤러 오류 및 내부 경고를 리포트 생성 데이터가 아닌 브라우저 console.log로만 격리 라우팅하여 리포트 오염을 방지함.

### 12) 리소스/크기: 지나치게 거대한 HTML 리포트 크기로 인한 브라우저 프리징
* **실수 내용**: 탐색을 완료한 최종 Markdown 및 HTML 대시보드 파일을 열면 웹 브라우저나 편집기 툴이 멈추거나 튕김.
* **원인**: 수십 장의 base64 스크린샷 데이터와 수만 줄의 IBM raw JSON 결함 덤프가 파일 하나에 인라인되어 파일 용량이 30MB를 초과함.
* **수정 조치**: 파일 생성 방식을 개편하여 base64 스크린샷 데이터를 ZIP 아카이브 내부의 별도 파일(`screenshots/screenshot_x.png`)로 추출해 상대 경로로 참조하게 하고, HTML 내에는 간결한 요약 대시보드 구조만 덤프하여 용량을 수십 KB 수준으로 경량화함.

### 13) 스토리지 한계: 대량의 화면 탐색 중 로컬 스토리지 할당량 초과 에러 발생
* **실수 내용**: 탐색 도중 30개 이상의 스크린이 넘어가면서 크롤러가 `QuotaExceededError`를 일으키며 멈춤.
* **원인**: Chrome extension Local Storage의 기본 5MB 용량 한계를 고려하지 않고 스크린샷을 누적 저장함.
* **수정 조치**: `manifest.json` 내 `permissions` 목록에 `unlimitedStorage` 권한을 명시하여 로컬 디스크 할당 제한을 극복함.

### 14) 중복 탐색: 오버레이 닫고 부모 화면 복귀 시 중복 스캔으로 시간 낭비
* **실수 내용**: 수량 선택 팝업이나 취침 예약 바텀시트 등을 닫고 원래 부모 화면으로 돌아왔을 때, 새로운 화면으로 오판해 불필요한 스캔을 재실행함.
* **원인**: 팝업이 닫히면서 부모 화면의 레이아웃 시그니처가 변경되어 다른 화면으로 인지함.
* **수정 조치**: 팝업 닫힘(`overlay-count-decreased`) 복구 완료 시, 이전 화면의 타이틀과 시그니처 구조를 대조하여 일치할 경우 스캔을 바이패스하도록 캐시 갱신 기능을 추가함.

### 15) 무한 스캔: 실시간 갱신 값(날짜/시간)으로 인해 매초 새로운 화면으로 인지함
* **실수 내용**: 기기 상세 화면 중 현재 시간이나 측정 수치가 실시간으로 변하는 화면에서 크롤러가 끝없이 새로운 스크린을 수집해 탐색 루프에 빠짐.
* **원인**: 화면 식별 시그니처를 해싱할 때 동적으로 실시간 갱신되는 텍스트 영역을 필터링하지 않고 날것으로 포함시킴.
* **수정 조치**: 텍스트 정규화(`normalizeText`) 단계에서 날짜 접미사, 초 단위 시간, 실시간 수치 데이터 패턴을 Regex로 정규화하여 순수 레이아웃 및 뼈대 시맨틱 텍스트로만 시그니처를 추출하도록 조치함.

### 16) 탐색 타임아웃: 수십 개 목록 아이템(식품 77개) 전수 진입 시도로 실행 중단
* **실수 내용**: 냉장고 식품 추가 같이 엄청나게 많은 카드 형태 아이템들이 있는 화면에서 제한 시간 내에 탐색을 끝내지 못하고 타임아웃으로 실패함.
* **원인**: 77개나 되는 야채 목록 각각을 전부 child screen으로 방문하려 함.
* **수정 조치**: 동일한 부모 구조를 가진 반복 리스트 개수가 5개 이상일 경우, 첫 번째, 마지막, 그리고 중간의 1개 무작위 아이템만 대표로 탐색을 수행하고 나머지는 스킵하는 3점 샘플링 알고리즘을 도입함.

### 17) 재현성 유실: 랜덤 샘플링 시 매 실행마다 결과가 달라져 재현성 상실
* **실수 내용**: 동일한 냉장고 화면에서 크롤러를 다시 돌렸을 때, 이전에 위배가 검출되었던 카드를 클릭하지 않고 다른 카드를 클릭해 결함 재현이 불가능해짐.
* **원인**: 샘플링 대상을 고를 때 `Math.random()` 비결정적 자바스크립트 API를 사용함.
* **수정 조치**: 텍스트 및 클래스명 해시와 전역 시드(`window.__thinqSeed__`)를 결합하여, 페이지 구조가 같으면 항상 동일한 특정 인덱스 카드들만 deterministic하게 선택되어 클릭되도록 알고리즘을 변경함.

### 18) 오버레이 갇힘: ThinQ generated picker modal 미인식
* **실수 내용**: ThinQ의 커스텀 시간/분/초 선택 모달이 떴을 때, 닫기 버튼을 찾지 못해 크롤러가 팝업 내부에서 계속 헛도는 현상.
* **원인**: 명시적인 모달 클래스가 없고 동적으로 생성되는 picker layout의 확인/취소 버튼 구조를 크롤러가 오버레이로 감지하지 못함.
* **수정 조치**: 클래스명에 modal/sheet 키워드가 없더라도 cancel/confirm 구조와 숫자 휠 컴포넌트가 존재하면 Generated picker modal 오버레이로 강제 식별하고 Escape나 native click으로 닫도록 처리함.

### 19) 오버레이 복구: 날짜 오버레이 복구 시 엉뚱한 부모 Back 클릭
* **실수 내용**: 날짜 피커 오버레이를 닫아야 하는 상황에서, 오버레이 내부의 확인/닫기 대신 화면 전체의 뒤로가기 버튼이 클릭되어 제품 상세 화면 밖으로 퇴출됨.
* **원인**: 오버레이가 떠 있음에도 복구 순서 상에서 최상단 부모의 back-button을 먼저 찾아 클릭함.
* **수정 조치**: 복구 시 오버레이 닫기 액션을 뒤로가기보다 우선순위로 두고, 백버튼 탐색 범위를 현재 active shell 내부로 한정하여 오버레이 외곽의 부모 back-button 클릭을 차단함.

### 20) 스크린샷: 캡쳐 API 실패 시 리포트 저장 과정 크래시
* **실수 내용**: 크롤링 중 네트워크나 딤드 로딩으로 인해 스크린샷 획득이 실패했을 때, ZIP 레포트를 패키징하고 다운로드하는 전체 프로세스가 크래시됨.
* **원인**: 스크린샷 바이너리 데이터가 null일 때의 에러 핸들링이 누락됨.
* **수정 조치**: 스크린샷 캡처 API 실패 시 예외를 포착(catch)하여 "No Screenshot captured" 텍스트를 대체 바인딩하고 레포트 압축 과정은 정상적으로 속행되도록 예외 처리 보강.

### 21) 연결 유실: Content Script 포트 단절 시 크롤러 먹통 현상
* **실수 내용**: ThinQ 페이지가 완전 새로고침되거나 다른 SPA 번들로 전환될 때 `Receiving end does not exist.` 오류가 뜨며 탐색이 즉시 중단됨.
* **원인**: 리로드 시 content script가 일시적으로 해제되어 Background worker와의 통신 포트가 단절됨.
* **수정 조치**: Background worker에서 메시지 전송 실패 감지 시, `chrome.scripting.executeScript` API를 이용해 해당 active tab에 즉시 `content.js`를 재주입(inject)하고 크롤러 실행을 이어서 진행하도록 복구 엔진 고도화.

### 22) 차트 제어: 차트 SVG 포인트 클릭 시도로 탐색 지연 및 불필요한 루프
* **실수 내용**: 공기청정기 초미세먼지 그래프 화면 내에 렌더링된 수십 개의 SVG 점(point)과 막대를 크롤러가 개별 클릭 후보로 인식하여 그래프 위에서 헛손질을 반복함.
* **원인**: SVG 엘리먼트에 clickable 스타일이 부여되어 단순 후보로 추출됨.
* **수정 조치**: SVG 차트 하위 요소들을 `chart-data-control` 및 `static-composite-container`로 정의하여 수집 필터에서 배제하고, 차트 노드 전체는 스냅샷 내에 정상 포함하여 IBM 접근성 검사의 평가를 받도록 최적화함.

## 3. 실수 반복 방지를 위한 핵심 행동 지침 (4대 절대 수칙)

### 수칙 1. 원인 파인딩(Root Cause Finding) 시 반드시 로그 분석 선행
* **지침**: 버그 및 오작동 신고가 접수되었을 때, 소스 코드부터 고치려 하거나 짐작으로 원인을 추측하지 않습니다. 에러가 발생한 시점의 **디버그 로그 데이터(TransitionLog, 시그니처 텍스트 등)를 열어 불일치 지점을 눈으로 직접 확인하고 팩트로 입증**한 뒤 원인 분석을 수립합니다.

### 수칙 2. 수정 후 정상 동작 여부도 로그 기반으로 교차 검증
* **지침**: 코드를 수정한 후 "화면이 잘 돌아가는 것처럼 보인다"는 정성적 판단으로 끝내지 않습니다. 수정 후 새롭게 수집된 **실행 로그 파일의 transitionLogs, signature value를 다시 열어 설계 계획대로 흘러갔는지 로그 기반 대조 검증**을 완료해야 합니다.

### 수칙 3. 단위 테스트(Unit Test) 작성 시 실제 로그 내 DOM 속성을 목킹
* **지침**: 단위 테스트를 작성할 때 임의의 짐작으로 DOM 구조를 구성하지 않습니다. **오류가 발생했던 실제 로그 및 캡처 데이터에 명시된 태그명, aria-selected, class, data-name 등의 속성과 구조적 레이아웃을 그대로 Mock DOM으로 재현**하여 실수를 잡아내도록 테스트 케이스를 설계합니다.

### 수칙 4. 사이드 이펙트(Side Effect) 및 기능 퇴화 여부 재차 더블체크
* **지침**: 새로운 픽스를 적용한 후에는 영향성 평가를 반드시 수행합니다. 이전에 통과했던 다른 가전제품군(WashTower, Refrigerator 등)의 탐색 시나리오나 유닛 테스트가 regression을 겪지 않는지 **전체 테스트 검증 파이프라인(`npm run verify`)을 실행해 재차 확인**하여 무결성을 보장합니다.
